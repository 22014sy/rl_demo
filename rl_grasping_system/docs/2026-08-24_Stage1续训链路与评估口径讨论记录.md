## 2. stochastic vs deterministic 评估区别（含本项目实测）

### 概念
策略本质是高斯分布 `π(a|s) ≈ N(μ(s), σ²)`。两者只是取动作的方式不同：

| | deterministic（确定性） | stochastic（随机） |
|---|---|---|
| 取法 | 取分布的**均值 μ** | 从分布**采样** a = μ + σ·ε（ε~N(0,I)） |
| 同一 obs 结果 | 每次都一样 | 每次不同，围绕 μ 波动 |
| 波动幅度 | 0 | σ（本项目 σ≈1.09~1.29） |
| 用途 | 部署/真机（稳定可复现） | 训练（需要探索） |

实现路径：`evaluate.py:71` `agent.predict(obs, deterministic=...)` → `agent.py:426-428`
（先 `vn.normalize_obs(obs)` 归一化观测，再调 SB3 `PPO.predict`）。

### 为什么差 14 pct
- deterministic 走 μ：±3cm 边界位置 μ 不够精确/不够激进 → "差一点点"失败。
- stochastic 加噪声：μ ± σ 级波动，部分样本"蒙到"成功动作 → 成功率被抬高。
- **σ 越大差距越大；σ 收敛小后两者趋近。** 训练 rollout 也是 stochastic，故 80% ≈ 训练 78.6%。

### 该信哪个
- **stochastic = 策略"会不会"（能力口径）**：80%，与训练一致。
- **deterministic = 部署保守下限（精度口径）**：66%。
- **验收/横向比较必须固定口径**：ROADMAP ≥70%、fixed 83.3% 均为 deterministic → stage1 的 66% **未达标**。
- 提升正确路径：**继续训练压低 σ**，让 μ 精确 → deterministic 自然追上 stochastic；不是用 stochastic 评估"凑达标"。

### 演练新发现（第 4 节方案之外）
1. **进程清理防误杀**：`pkill -f 'final_stage1_[d]rill'`——方括号正则避免把执行命令的 shell 自身
   （其 cmdline 含字面量）也杀掉。
2. **并行启动命令的 cd 陷阱**：`cd x && A & B &` 解析为 `{ cd x && A } & { B } &`，**B 在旧目录跑**
   （本次 stochastic 评估因此报路径不存在）→ 并行启动必须把 `cd` 放进每个后台 job。
3. **续训收尾会再存一次 checkpoint**：续训 num_timesteps 从 0 走满 98304（=目标）时，SB3 又保存
   `{prefix}_98304_steps.zip` + SB3 命名 pkl（对应 zip 删除后留孤儿 pkl，需一并清理）。
4. **并行训练实例要防重复启动**：本次发现 drill 被启动两份（两个独立 setsid session，各 13 进程、
   写同一日志）→ load 接近 29、rollout 间隔翻倍；已全部清理后重启单实例。
   教训：后台启动后应确认进程数 ≈ 1 + n_envs，而非盲目相信 job 报告（`setsid` 分离后 bash 的
   `[n] Done` 可能是 wrapper 退出而非训练结束）。

### 口径再印证
演练模型（stage1 + 0.2M 步续训）deterministic 70.0% vs stochastic 80.0%——确定性仍低于
ROADMAP ≥70% 线（仅踩线），与"σ≈1.1~1.3 偏大、需继续训练压低方差"的既有结论一致；
train rollout 79% ≈ stochastic 80%，能力口径自洽。

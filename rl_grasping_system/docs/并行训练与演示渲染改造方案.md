# 并行训练 + 定期演示渲染 改造方案

> 记录 2026-08-22 的讨论结论与实施计划：解决「模型训练成功率不高且很慢」。
> 状态：**✅ 已实施完成**（2026-08-22，工程变更见 CHANGELOG.md 顶部条目）。

---

## 一、现状问题与硬证据

最近一次训练（`training.log` 2026-08-22 11:35 → 13:02，40000 步，`train_with_monitor.py`）：

| 指标 | 数值 |
|---|---|
| 训练吞吐 | ~7.7 步/s（87 分钟 40000 步；每 rollout 1024 步 40-60 秒） |

## 二、根因诊断

### 慢的根因（按权重）

1. **单环境串行采样**：`SystemConfig.num_envs=1`，`agent.py` 用 `DummyVecEnv([lambda: env])` 只有 1 个环境，16 核只用 1 核。RL 吞吐 = 单环境采样速度。
2. **每决策步物理计算极重**：每步 = `action_repeat(2) × substeps(10) = 20 次 mj_step`，且速度模式下**每个物理子步**都重复执行 `velocity_ik`（雅可比+阻尼伪逆）和 `mj_fullM`（全质量矩阵）+ PID + 惯性/重力前馈（`environment.py` 速度模式物理循环）。目标速度一整个决策步内不变，IK/质量矩阵存在去重空间。
3. **全程 GLFW 渲染**：`config.render_gui=True` 为默认值，`train_with_monitor.py` 未关闭 → 40000 步全程开窗渲染。
4. **Episode 过长**：`max_steps=300`，初始位形本就悬在物体上方附近，大量步数浪费在失败漫游。

### 成功率低的根因

1. **样本总量太少**：40k 步 ≈ 136 episodes，对 6D 连续控制抓取任务远不够（通常需百万级）。
2. **6D 动作空间 + 方向奖励被禁用**：`action_space_dim=6`，但 `config.w_orient=0.0`（与 DEV_LOG 声称恢复的 3.0 不一致）→ 姿态维度无梯度，纯靠熵随机探索。
3. **成功奖励链太长太稀疏**：要拿 `grasp_reward=100` 需走完「对齐(4.5cm XY + 3.2cm Z) → 闭合 → 3 步宽度收敛 + 双指接触」，任一环失败全链落空。
4. **策略不稳定/退化**：单环境小 batch 更新方差大 + `ent_coef=0.005` 过低；后期大量奇异点惩罚（`-0.5/步`）。

### 验证脚本实证（2026-08-22，全部执行过）

| 脚本 | 结果 | 关键输出 |
|---|---|---|
| `verify_grasp_feasibility.py` | **PASS** | IK 误差 0.0002m，闭合后开度 0.0627m > 0.02，双指接触正常 |
| `verify_grasp_success_criterion.py` | **PASS** | 正确抓取→closed+success；侧方→不误触发；滞回→可重试 |
| `verify_ee_pose_control.py` | **PASS** | 30 步 dx 移动 0.137m、姿态旋转 75.4°、零动作漂移 5.8e-9 |
| `diag_orientation_reward.py` | **❌ 方向奖励恒为 0** | 朝下/朝上/水平三姿态 `r_orient` 全为 0（`w_orient=0.0` 实证） |

**结论**：环境物理链路与动作执行均正常，成功率低的根因集中在「样本量不足 + 姿态维度无学习信号 + 奖励链稀疏」。

## 三、已确认的实施方案

> 需求约束：不关闭渲染（但要保留并行提速）→ 采用 **多进程并行训练（worker 全无头）+ 主进程定期自动播放演示窗口**。

### 改动清单

| 文件 | 改动 |
|---|---|
| `config.py` | `num_envs` 1→12；`n_steps` 1024→2048；`n_epochs` 5→10；`total_timesteps` 40000→200000；`max_steps` 300→200；`action_space_dim` 6→3；`w_orient` 0.0→3.0；`render_gui` True→False |
| `agent.py` | `DummyVecEnv`→`SubprocVecEnv`（12 worker，工厂函数在子进程内新建环境，worker 内包 `Monitor`）；`GraspingCallback` 增加演示机制（`demo_env` + `demo_every_n_rollouts`，每 N 个 rollout 用当前策略跑 1 个 episode 弹窗播放） |
| `environment.py` | 速度模式物理循环 IK 去重：`velocity_ik` 每控制周期 1 次、`mj_fullM` 每决策步 1 次（需重跑 `verify_ee_pose_control` 确认实现率不掉） |
| `singularity_handler.py` | 初始位形 `spread` 0.3→0.15（课程式：先学近端精确，后续可放开） |
| `train_with_monitor.py` | 显式 `render_gui=False`（训练无头）；主进程创建演示环境（`render_gui=True`）传入 agent |

### 关键实现要点

- `SubprocVecEnv` 的 worker 必须**在子进程内新建环境**（MuJoCo model/data 不可 pickle；工厂函数本身可 pickle）。
- 演示环境走 `self.model.predict`（自动经 VecNormalize 归一化），`render_interval=1` 全程渲染。
- 演示频率默认每 5 个 rollout（≈10k 决策步）1 次、每次 1 个 episode；期间训练主进程短暂暂停几秒，整体影响小。
- 内存：12 worker × ~400-600MB ≈ 6GB，11GB 内存足够；若吃紧降为 8 worker。

### 预期效果

- 吞吐：~7.7 步/s → ~50-80 步/s（约 6-8 倍），200k 步约 1 小时跑完。
- 成功率：3D 动作空间 + 方向梯度恢复 + 样本量 ×5，有望取代 A2 靠初始位形运气的 5.1%。

### 验证步骤

1. `verify_ee_pose_control.py`：IK 去重后动作实现率不降。
2. 短训 smoke（5k~10k 步）：12 进程正常、无崩溃、演示窗口能弹。
3. 对比每 rollout 耗时（原 40-60s → 理论 ~7s）。
4. 完整训练后 `evaluate.py` 独立评估（已带 VecNormalize 加载）。

## 五、实施结果（2026-08-22 实测）

| 验证项 | 结果 |
|---|---|
| `verify_ee_pose_control.py` | **PASS**（适配 3D 动作空间后）；dx 30 步 0.137m，与 IK 去重前完全一致，实现率不受影响 |
| `verify_grasp_success_criterion.py` | **PASS**（抓取链路完好） |
| smoke 并行训练（12 环境 / 24576 步） | **PASS**：fork 正常、无 XIO 错误；**吞吐 70.9 步/s（原 7.7，↑9.2 倍）** |
| TrainingMonitor 主进程汇总 | 120 episodes 正常写入 JSON（多进程下无文件冲突） |
| demo_env 渲染链路 | viewer 弹出、30 步渲染 OK（退出时 `GLXBadDrawable` 告警无害） |

**实测中额外修复的两个问题**（实施计划之外）：
1. **fork 后 XIO fatal error**：SB3 SubprocVecEnv 的 worker 继承主进程 GLFW/X 连接。
   修复 = `environment.py` 中 `render_gui=False` 时不创建 Renderer + `train_with_monitor.py`
   调整顺序（先 fork 再建 demo_env）。
2. **forkserver 依赖 `__main__` 保护**：SB3 在 Linux 默认 forkserver。修复 = `agent.py`
   显式 `start_method="fork"`（Linux），不依赖调用方写法。


- **课程学习（两阶段：先到达后抓取）**：本轮不做，先用 3D 动作空间验证链路。
- **闭合触发 shaping（进入 closing 给小奖励）**：留待 3D 训练看接触出现情况后再决定。
- **HER**：暂不引入。
- **IK 去重影响动力学保真**：若 `verify_ee_pose_control` 实现率明显下降（<90%），回滚该优化，只保留多进程并行。
